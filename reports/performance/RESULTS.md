# MsgMate 性能测试结论与证据

测试日期：2026-10-10。

## 环境与范围

- WSL2，Intel i9-13900HX，可用 32 个逻辑 CPU；内存总量约 7.6 GiB、Swap 2 GiB。`.wslconfig` 未显式设置 memory/processors/swap，仅设置 dnsTunneling 和 autoProxy。
- 暂停 12 个无关 Docker 容器后进行测试；结束后恢复。测试服务、负载客户端和依赖同机运行，使用独立 Compose project、数据库、Redis、Kafka/Zookeeper 和 Docker 私网。
- 真实 Go/Gin/GORM 路由、MySQL 8.0.46、Redis、Kafka 7.6.1 及生产队列消费者；使用 EMAIL=1 的进程内零延迟模拟渠道，不调用真实 SMTP、短信或飞书 API。
- Kafka 四个 Topic 各单分区、单副本；生产源码同步发布、ack=-1；kafka-go v0.4.47 的默认 BatchSize=100、BatchTimeout=1 秒。没有调整生产消费算法、MySQL 50/10 连接池或这些 batching 参数。
- 保持 info 和 Gin 访问日志，但写文件，不向 IDE 终端刷屏。独立测试入口不启动定时消费者或启动恢复；生产环境中的这些成本不在测试内。
- 记录查询轮转 10,000 条合成记录，直接读取 MySQL，不读取 Redis 记录缓存。队列实验中的记录数随各档逐步增加，详见每轮 before/after 计数。

## 阈值与失效点

- **查询**：短档曾达到约 1.1 万 req/s；32 并发长档发生数据库连接错误，不能把短峰值当稳定能力。8 并发已接近约 1 万 req/s的平台并通过复测；没有证明 8 是最大可用并发。
- **MySQL 入口**：吞吐平台约 3.8k req/s；1,024 并发出现 18 次 timeout。512 并发两次复测无错误，但高并发带来约 580ms 的 P99。入口测试关闭业务消费处理，只测持久化与入队，不代表持续消费能力。
- **Kafka 入口**：吞吐平台约 4.7k req/s；1,024 并发出现 8 次 timeout。256 并发选作复测点；512 并发短档也达标，吞吐几乎没有增长、P99 增大，不能称 256 为最大可用并发。
- **MySQL 消费**：已验证 80 条/s；90 条/s 新专项测试虽然 2,700 条最终全部成功，但积压增长约 4.4 条/s，停止观察时仍有 69 条，需继续等待排空。持续速率边界在 **80–90 条/s**，90 不作为稳定容量。证据：[001-queue-mysql-r90](20261010-124946/001-queue-mysql-r90.json)。
- **Kafka 消费**：已验证 150 条/s；160 条/s 首个 30 秒测试积压增长约 33.5 条/s、停止观察时剩 450 条。之后 120、140、150 条/s 长档与两次 150 条/s 复测达标。当前边界为 **150–160 条/s**，并非 Kafka Broker 的硬件极限。

上述区间是固定负载分布、数据规模和实验判据下的可复现边界。入口、完成速率必须分开使用；不能从“最终都处理完”推出“该到达速率长期不积压”。

## 实际定位的瓶颈

查询长档捕获：`dial tcp ...:3306: connect: cannot assign requested address`。同一轮 Go 容器 MySQL TIME_WAIT 达 28,221 个，接近临时端口范围 32768–60999（28,232 个）。SQL 连接池最大打开 50、最大空闲 10；高并发下累计 MaxIdleClosed 约 2.97 万，说明大量连接被关闭并反复创建。此证据支持连接回收与端口耗尽的因果判断；未在本次测试中修改连接池并验证优化收益。

证据：[32 并发错误样本](20261010-121707/006-record-mysql-c32-samples.json)、[32 并发结果](20261010-121707/006-record-mysql-c32.json)。该问题必须连同短时峰值一起说明，不能只挑峰值写简历。

MySQL Low 消费每次取 10 条，逐条处理后随机等待 1–500ms；Kafka 每个优先级顺序处理并同步提交 offset。这些源码行为解释了消费能力与受理能力的差异，但没有对它们做独立归因或参数优化实验。

## 日志、修正和可复核性

- [完整入口/查询/MySQL 消费日志](20261010-121707/TEST_LOG.md)、[Kafka 长档专项日志](20261010-123904/TEST_LOG.md)、[MySQL 90 条/s补测](20261010-124946/TEST_LOG.md)。每轮包含原始 wrk/负载输出、业务计数、池等待、状态采样；resource-samples.jsonl 是运行期间容器 CPU/内存样本。
- 首次脚本的消费完成速率窗口误纳入负载结束后的时间，导致 Kafka 10 条/s短档偏低；该短档不作为容量结论。随后修正为只取负载持续期间，并用服务端时间戳计算速率，重新完成 Kafka 专项测试。
- 入口测试和队列测试分开 Kafka Topic；入口每档清理自己的合成数据，防止残留记录与消息污染后续测试。
- MySQL 独立脚本曾因镜像初始化阶段的 Unix socket 健康检查提前成功而启动失败，未产生压测请求。健康检查已改为 TCP 就绪；90 条/s专项测试确认独立启动正常。
- 最终脚本还增加停止观察时的尾部积压上限 max(10,目标速率×0.25)。首次完整运行保存了当时 runner-used.py，SHA256 与 environment.json 中运行时脚本哈希相同；本结论选用的 80/150 条/s复测在停止时均为零积压，也满足更严格判据。
- 排空计时从控制器观察负载进程结束后开始，约 2 秒轮询检测间隔会影响该值，不能拿它宣称单条消息送达 SLA。
- 运行基于工作区源码，已有未提交修改；环境文件保留 Git HEAD、状态、源码及二进制 SHA256，不宣称远端已验证当前结果。
